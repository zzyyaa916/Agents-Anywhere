# Fork 2.7.1 消息排序修复

本分支接在 2.7.0 探针修复之后；PR 比较基线应选 fix/con+be/usage-probe-reliability，只审查排序差异。

## 核实结果

- timeline_items 的 (session_id, order_seq) 只有普通索引，没有唯一约束；没有增加可能被存量数据阻塞的唯一索引。三处增量写入在现有会话 fence / PostgreSQL advisory 事务锁内查询占位并写入，缓冲持久化再次检查冲突。已有 ID 始终保留 durable 位置。
- 正常分布式写入使用 Redis session-revision:<session_id> fence，持久化再取 session_timeline_lock_key 的 PostgreSQL advisory 事务锁；脚本使用相同机制。
- 表中没有独立 created_at 列，创建时间在 payload_json.createdAt 中；修复按带时区的创建时间、旧 order_seq、ID 排序。
- PiClient 的合成 user 回声携带 _meta.aa.clientMessageId；通用 ACP v1 不保证携带，后者只使用当前明确回合关联，不按文本去重。

## 行为与存量修复

空闲且合法的 int32 自报序号按原位接收，冲突或超范围追加至 max+1；追加溢出时拒绝，已有条目序号不变。beforeOrderSeq 仍严格小于游标。同批次抢位先到先得。原有缓冲溢出修复路径保留。

server/scripts/reorder_session_timeline.py 已提供，只写未运行。默认 dry-run，读取指定会话并输出序号规划，不写库；正式 --apply 必须指定 --backup，使用部署相同的 Redis URL / prefix，以同一 fence 排空已接收缓冲，再进入 DB advisory 事务。成功导出 0600 独占备份后，先整体偏移到验证过的 int32 安全空间，再重写连续序号和 payload，并发布 reset fence。空间不足、原序号重复或配置不足时停止。正式执行仍须用户确认；本次没有生产 session_id / 数据库连接，未取得实际 dry-run 输出。
